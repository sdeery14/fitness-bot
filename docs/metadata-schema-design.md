# Metadata Schema Design

## Problem Statement
Frontend requires additional metadata fields that were previously stored in the `plan_snapshot` JSON column. We need to add proper structured columns/tables to store this data.

## Required Metadata Fields

### 1. Fitness Plan Level Metadata
These apply to the entire plan:

```python
- key_principles: List[str]  # Core principles guiding the plan
  Example: ["Progressive overload", "Adequate recovery", "Consistent nutrition"]

- success_metrics: List[str]  # How to measure success
  Example: ["Increase bench press by 20%", "Lose 10 lbs", "Complete 5K"]

- important_notes: str  # Critical information
  Example: "Consult doctor before starting. Always warm up properly."
```

**Storage Decision**: Add to `fitness_plans` table as JSON columns
- Flexible for variable-length arrays
- Plan-specific, not reused across plans
- Simple queries: `SELECT key_principles, success_metrics, important_notes FROM fitness_plans WHERE id = ?`

### 2. Workout Plan Metadata
Applies to the workout plan:

```python
- phase_progression_notes: str  # How phases progress
  Example: "Each phase increases volume by 10%"

- equipment_used: List[str]  # Required equipment
  Example: ["barbell", "dumbbells", "bench", "pull-up bar"]
```

**Storage Decision**: Add to `workout_plans` table
- Direct relationship to workout plan
- Used for display and planning purposes

### 3. Meal Plan Metadata
Applies to the meal plan:

```python
- dietary_approach: str  # Diet philosophy
  Example: "Flexible IIFYM with whole foods focus"

- macro_strategy: str  # Macro distribution strategy
  Example: "Higher carbs on training days, lower on rest days"

- meal_timing: str  # Meal timing guidance
  Example: "Protein within 2h of training, carbs around workouts"

- hydration_guidance: str  # Water intake guidelines
  Example: "3-4L per day, more on training days"

- phase_nutrition_notes: str  # How nutrition changes across phases
  Example: "Increase calories 200/week during bulk phase"
```

**Storage Decision**: Add to `meal_plans` table
- Direct relationship to meal plan
- Provides context for the meal planning strategy

## Implementation Plan

### Phase 1: Database Schema Updates

#### 1.1 Add columns to `fitness_plans`
```sql
ALTER TABLE fitness_plans 
ADD COLUMN key_principles JSON,
ADD COLUMN success_metrics JSON,
ADD COLUMN important_notes TEXT;
```

#### 1.2 Add columns to `workout_plans`
```sql
ALTER TABLE workout_plans
ADD COLUMN phase_progression_notes TEXT,
ADD COLUMN equipment_used JSON;
```

#### 1.3 Add columns to `meal_plans`
```sql
ALTER TABLE meal_plans
ADD COLUMN dietary_approach TEXT,
ADD COLUMN macro_strategy TEXT,
ADD COLUMN meal_timing TEXT,
ADD COLUMN hydration_guidance TEXT,
ADD COLUMN phase_nutrition_notes TEXT;
```

## Benefits

1. **Type Safety**: Proper column types instead of nested JSON
2. **Query Performance**: Direct column access instead of JSON path queries
3. **Data Integrity**: Database constraints on required fields
4. **Clarity**: Clear schema that documents what data exists
5. **Maintainability**: Easy to update individual fields without parsing JSON

## Migration Strategy

1. Create Alembic migration for schema changes
2. Existing plans will have NULL values (acceptable - they're historical)
3. New plans generated by AI will populate all fields
4. Frontend handles missing fields gracefully (optional chaining)

## Alternative Approaches Considered

### Option A: Keep in JSON columns
- ❌ Less type safety
- ❌ Harder to query
- ❌ Less clear schema
- ✅ More flexible

### Option B: Separate metadata tables
- ✅ Most normalized
- ❌ Overkill for 1:1 relationships
- ❌ More complex queries with extra joins
- ❌ More tables to manage

### Option C: Add columns (CHOSEN)
- ✅ Clear, queryable schema
- ✅ Good balance of normalization
- ✅ Simple queries
- ✅ Easy to understand and maintain
